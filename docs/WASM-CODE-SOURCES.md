# Source-bound IL2CPP/WASM method evidence

`monkey.wasm_code_sources.inspect_wasm(source, output, *, expected_source_sha256, metadata, expected_metadata_sha256, method_map, expected_method_map_sha256, decoded_segments, method_ids=None, brotli_provider=None)` validates a compressed WASM source, raw IL2CPP global metadata v29, a selected-method map, and caller-supplied decoded-segment rows. Each `decoded_segments` row uses `segment`, `path`, `expected_sha256`, `index_path`, `expected_index_sha256`, `source_path`, and `source_sha256`. It independently walks the decoded WASM section table and code-body boundaries, compares the existing segment index, verifies method-map type/method indices and tokens against the exact metadata bytes, and checks every map offset/size/hash against the actual function body bytes. It also compares an existing selected body snapshot when one is present. An explicit `brotli_provider` is an executable CLI path invoked as `provider -d -c <source>`; it is hashed before use, limited to a 120-second deadline, and its stdout is stopped as soon as it exceeds the exact byte length of the single mapped segment. The decoded output must byte-for-byte and SHA-256 match that segment. Without this argument, the decode link remains caller-manifest-only.

The report ties together exact bytes while keeping the evidence levels separate. With the optional provider, the report labels the link `verified_brotli_bytes` and records the provider path/hash, output byte count, and output hash; otherwise it remains caller-manifest-only. Metadata rows cross-check with the v29 TypeDef/MethodDef indices and tokens, but the report explicitly withholds a claim that metadata and WASM share an independently established build ID. The `metadataMethodIndex`→`functionIndex` association still comes from the caller-supplied map: this module does not parse IL2CPP `codeRegistration`, so those matching identities, tokens, and body offsets do not independently authenticate that association. Consequently generated FP C# candidates retain that map-association assumption. Source code, DLL, JavaScript, and WASM execution are always false; this module reads and copies bounded byte slices only.

`monkey.wasm_code_semantics.recover_wasm_subset(report_or_receipt, output, *, selections)` currently emits candidate C# replacement fragments only for `BattleCore.FP` two-operand `i64` arithmetic and comparison bodies whose complete function body is exactly local0, local1, one supported operation, return, and end. The raw function type must match the IL2CPP WASM ABI: two `i64` value arguments, one trailing `i32` method-context pointer, and an `i64` or `i32` result as appropriate. The lifted methods are addition, subtraction, equality/inequality and signed order comparisons. The output fragments are generated from opcode bytes and the map signature; the integer additions/subtractions use C# `unchecked` arithmetic to preserve WebAssembly i64 wrapping. Equality/order operators are emitted in required C# pairs when the paired body exists in the supplied report set.

All other mapped bodies remain `body_evidence_only` with a limitation. The current normal-wave and trigger slice includes object field loads/stores, lazy runtime initialization, calls whose target functions lack exact method identities in the selected map, or larger stateful routines. Their exact bodies are validated and retained, but this module does not infer C# from `wasm-decompile` pseudocode, source-level method names, or already hand-ported game code. The independently recovered FP operator fragments are useful method bodies, not evidence that the normal-wave methods or the full game have been ported.

The generated `CSharpCandidate/FP.RecoveredOperators.cs` is an isolated fragment for merging into the existing `BattleCore.FP` declaration; it does not copy or replace the whole struct. A self-owned fixture can add the same raw-value field, compile the fragment, and exercise signed comparisons and wrapping arithmetic. The minimal fixture reports the normal C# warnings for defining `==`/`!=` without reimplementing `Equals`/`GetHashCode`; those unrelated methods are not invented in this subset. This fixture only validates the generated candidate, not original WASM execution or runtime parity.

## CLI

```sh
monkey wasm-code-source --source module.wasm.br --expected-source SOURCE_SHA --metadata global-metadata.dat --expected-metadata METADATA_SHA --method-map selected-method-map.json --expected-method-map MAP_SHA --decoded-segments decoded-segments.json --brotli-provider /path/to/brotli --method-id EXACT_ID --out wasm-source
monkey wasm-code-candidate --source-report wasm-source/wasm-code-source.json --expected-report REPORT_SHA --method BattleCore.FP::op_Addition --out wasm-candidate
```

The first JSON argument is the explicit array of decoded-segment rows described above. Both commands return exit 1 for partial evidence/candidate results; inspect their reports. Multiple source reports can be passed as repeated `--source-report` / `--expected-report` pairs in matching order, with one pinned SHA per report. Reports must share the exact metadata and method-map identity. Duplicate methods and ambiguous qualified symbols fail; use exact method IDs for overloads. At most eight reports and 256 selection strings are accepted. The candidate stage rechecks report and body hashes before writing. A successful fragment is not a standalone FP library: the existing partial struct/raw-long field must be independently validated by the adopting developer.
